# Розгортання на бойовому оточенні

Порядок дій від «є акаунти клієнтки» до «сайт на домені». Розраховано на одну
людину й приблизно пів дня, з яких більшість — очікування DNS.

Усі сервіси реєструються **на клієнтку**, не на нас: після проєкту вона має
лишитись власницею всього. Ми лише отримуємо доступ.

---

## 0. Що має бути на руках

Перелік із поясненнями, де що брати, — у `estimate/Доступи_і_ключі_MK.pdf`.
Мінімум, без якого немає сенсу починати:

- домен і доступ до DNS;
- WayForPay: merchant login і секрет;
- токен Telegram-бота, бот доданий адміністратором у канали курсів;
- пошта, на яку реєструються сервіси.

---

## 1. База даних (Neon)

1. `neon.tech` → новий проєкт, регіон **Frankfurt** (найближчий до України).
2. Скопіювати connection string (`postgres://…?sslmode=require`) — це `DATABASE_URI`.
3. Увімкнути **Point-in-time restore** (на безкоштовному тарифі — 7 днів).

Схему створюють **міграції** з `src/migrations/`. Вони запускаються самі при
кожній збірці на Vercel: у `vercel.json` стоїть
`"buildCommand": "payload migrate && next build"`. Тобто перший деплой сам
розгортає всі таблиці на порожній базі Neon, а кожен наступний застосовує лише
те, чого ще не було. Повторний запуск безпечний: застосовані міграції
пропускаються.

Команда живе саме у `vercel.json`, а не в `build` у `package.json`, і це не
випадково. Локальна база працює в режимі push і має службовий запис `dev`
(`batch = -1`), а `payload migrate`, побачивши його, зупиняється й **чекає на
підтвердження з клавіатури**. Якби міграція стояла в `build`, звичайний
`npm run build` у розробника висів би назавжди без жодного повідомлення. На
чистій базі прода такого запису немає, тож там команда неінтерактивна.

Режим push тут НЕ працює, і покладатися на нього не можна. У самому Payload
стоїть умова `process.env.NODE_ENV !== 'production'` — на Vercel змінна завжди
`production`, тож схема ніколи не розгорнулася б автоматично, і сайт піднявся б
на базі без жодної таблиці. У розробці push лишається: локально схема
оновлюється сама, а в базі стоїть службовий запис `dev`.

Після зміни полів у колекціях:

    npm run migrate:create <коротка-назва>   # згенерувати міграцію зі змін
    npm run migrate:status                   # що застосовано, а що ні

Згенерований файл треба **закомітити** — без нього прод не дізнається про зміну.

> Перед злиттям варто прогнати міграцію на порожній базі, а не лише на своїй:
> `createdb` поруч, `DATABASE_URI=… NODE_ENV=production PAYLOAD_MIGRATING=true npm run migrate`
> і звірити кількість таблиць із робочою. Саме так ловиться випадок, коли
> міграція спирається на дані, яких на чистій базі ще немає.

## 2. Сховище файлів (S3 або Cloudflare R2)

R2 простіший і дешевший, S3 — звичніший. Що завгодно з двох:

1. Створити бакет `mk-media`.
2. Створити ключ доступу з правами лише на цей бакет.
3. Дозволити публічне читання об'єктів (запис — тільки за ключем).
4. CORS: дозволити `GET` з бойового домену.

Змінні: `S3_BUCKET`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`,
`S3_ENDPOINT`. Порожній `S3_BUCKET` — файли лягають локально, для прода не годиться.

---

## 3. Пошта (Resend)

1. `resend.com` → API key.
2. Domains → Add Domain → додати видані DNS-записи (SPF, DKIM, DMARC) у зоні домену.
3. Дочекатись статусу **Verified** — інакше листи підуть у спам.

`RESEND_API_KEY`, `EMAIL_FROM` (наприклад `MK <shop@домен>`).

---

## 4. Проєкт на Vercel

1. Імпортувати репозиторій, фреймворк визначиться сам (Next.js).
2. Регіон функцій — `fra1` (уже вказаний у `vercel.json`).
3. Додати змінні оточення (див. `.env.example`), обовʼязково:
   - `PAYLOAD_SECRET` — довгий випадковий рядок, згенерувати новий, не брати з локального;
   - `DATABASE_URI`, `NEXT_PUBLIC_SERVER_URL` (бойовий домен, з `https://`);
   - S3, Resend, WayForPay, Telegram;
   - `CRON_SECRET` — довільний довгий рядок. Vercel сам додає його як
     `Authorization: Bearer …` до планових викликів.
4. Deploy. Перевірити, що `/admin` відкривається.

`vercel.json` уже налаштовує щоденний виклик `/api/marketing/abandoned-cart`
о 10:00 UTC — лист про кинутий кошик.

---

## 5. Домен

1. У Vercel: Project → Domains → додати домен і піддомен `www`.
2. У реєстратора прописати видані записи.
3. Дочекатись сертифіката (зазвичай хвилини, іноді до години).
4. Перевірити, що `http://` і `www` перекидають на основний `https://`.

---

## 6. Наповнення й перенесення

```bash
npm run seed:content                      # службові сторінки, якщо база порожня
npm run import:products -- товари.csv dry # перевірка файлу клієнтки
npm run import:products -- товари.csv     # реальний імпорт
```

Товари створюються **чернетками**: фото додаються в адмінці, далі публікація.

Перенаправлення зі старого сайту вже прописані в `src/lib/redirects.ts`
(`/oplata`, `/publichna-oferta`, `/pitannya-ta-vidpovidi`,
`/politika-konfidenciynosti`). Після запуску пройтись по посиланнях зі старого
сайту й дописати те, що знайдеться.

---

## 7. Платежі

1. WayForPay → додати бойовий домен у мерчант (він має збігатися з `NEXT_PUBLIC_SERVER_URL`).
2. Service URL: `https://домен/api/payments/wayforpay/callback`.
3. Замовити ввімкнення Apple Pay і Google Pay у підтримці.
4. **Тестова покупка на реальну картку** — найдешевша перевірка з можливих:
   - гроші списались, статус замовлення став «Оплачено»;
   - лист із доступом прийшов;
   - запрошення в Telegram-канал одноразове;
   - фіскальний чек прийшов на пошту (якщо підключено Checkbox);
   - залишок списався.
   Потім — повернення коштів із кабінету WayForPay.

---

## 8. Аналітика

`NEXT_PUBLIC_GA_ID`, `NEXT_PUBLIC_META_PIXEL_ID`, `META_CONVERSIONS_TOKEN`.

Перевірка серверної події: Events Manager → Test Events. Покупка має прийти
двічі (з браузера й з сервера) і **склеїтись в одну** за номером замовлення.
Якщо видно дві окремі — не збігається `event_id`.

## 10. Після запуску

- Google Search Console: підтвердити домен, надіслати `sitemap.xml`.
- Перевірити `robots.txt` — на проді має дозволяти індексацію.
- Перевірити, що `/admin` не в індексі (він закритий у robots).
- Передати клієнтці доступи, змінити паролі, які бачив розробник.
